# AGENTS.md

This repository is a Go web server template for REST APIs and small HTML surfaces. It uses Cobra/Viper for configuration, `net/http` for routing, `sqlc` for database access, embedded SQL migrations for schema changes, `templ` for HTML, Redocly for OpenAPI docs, and small internal interfaces for auth, database, permissions, localization, middleware, and cache behavior.

## Project Shape

- `cmd/`: CLI commands and runtime wiring. `cmd/serve.go` handles Cobra/Viper configuration, `cmd/server.go` wires dependencies and runs the HTTP server, and `cmd/logging.go` constructs the logger.
- `handlers/`: HTTP route registration and endpoint implementations. Keep related endpoints together: account endpoints belong in `account.go`; a new `/myendpoint/...` group should usually get `myendpoint.go` with `registerMyEndpointRoutes`.
- `middleware/`: HTTP middleware. Middleware should depend on small function/interface types where practical, such as `LocalizeFunc`, instead of depending on full handler state.
- `database/`: database interfaces, models, migrations, sqlc config, and backend implementations.
- `database/postgres`, `database/sqlite`, and `database/mysql`: backend-specific migrations, generated sqlc packages, and query adapters.
- `database/cached`: database read-through cache wrapper. Keep cache logic here, not in handlers.
- `cache/`: small byte-oriented key-value cache interface and memory implementation.
- `auth/`: JWT claims and authenticator construction.
- `database/models.go`: application-facing models and role and permission keys.
- `i18n/`: locale maps exposed through copying `Locales()`. User-facing strings and error messages should be represented by stable keys.
- `docs/api.yaml`: OpenAPI source. `handlers/static/api/index.html` is generated and ignored.
- `templates/`: `templ` HTML templates.

## Adding an Endpoint

1. Decide the route group and file.
   - Add account-specific routes to `handlers/account.go`.
   - Add a new file like `handlers/myendpoint.go` for a new `/myendpoint/...` group.
   - Add a `registerMyEndpointRoutes()` method and call it from `Handler.registerRoutes()` in `handlers/handler.go`.

2. Choose route protection.
   - Public endpoints can use `h.Add(method, "/path", h.HandlerFunc)`. `Add` and `AddHandler` apply the configured root prefix; pass application-relative paths.
   - `NewHandler` validates the configured root prefix before registering routes. Prefixes must be clean literal paths without wildcards, percent encoding, dot segments, repeated interior slashes, whitespace, control characters, backslashes, query strings or fragments. Surrounding whitespace and trailing slashes are normalized; a missing leading slash is added.
   - Authenticated endpoints should use `middleware.AuthenticateBearer(h.logger, h.localize, h.authenticator, next)`.
   - Authentication stores a validated `middleware.Identity`. Account handlers use `h.requireIdentity(w, r)` to retrieve its claims and numeric subject.
   - Permission-protected endpoints should wrap authentication plus `middleware.RequirePermission(...)`.
   - Add new middleware only when behavior is reusable across endpoints. Keep endpoint-specific validation inside the handler.
   - Request logging wraps the mux once in `NewHandler`, including responses generated by the router.

3. Keep request/response handling consistent.
   - Define request/response structs near the handler that uses them unless they are shared.
   - Use `decodeBody[Request](h, w, r, errorKey, logMessage)` in handlers; it uses `internal/httpx.DecodeJSON` to enforce a 1 MiB limit, unknown-field rejection and a single JSON value. Keep request/response types at package scope beside their handler.
   - Use `httpx.WriteJSON` for JSON success responses. Handlers and middleware share the writer in `internal/httpx`, including `no-store`.
   - Use `h.writeStatus` or `h.writeError` for error responses so logs and localized JSON error bodies stay consistent.
   - Format `h.writeStatus` and `h.writeError` calls one argument per line when they have localization keys or log args.

4. Localize messages and errors.
   - Keep localization keys stable; request-body and confirmation-body keys represent different operations and need not be renamed just for symmetry. Use normal Spanish accents in translations.
- Error keys should be stable and concise, for example `err.select_account`, `err.invalid_login_body`, or `err.permission_denied`.
   - Add every new error key to both `i18n/en.go` and `i18n/es.go`.
   - Add user-visible role or permission labels as keys like `role.default` or `perm.change_email`.
   - Keep logs as clear English messages; keep response bodies localized through keys.

5. Update API docs.
   - Add the endpoint, request body, response schemas, auth requirements, and error responses to `docs/api.yaml`.
   - Run `npm run redocly` after docs changes.
   - Do not manually edit generated `handlers/static/api/index.html`.

## Database Changes

1. Add migrations for every backend.
   - Postgres migrations go in `database/postgres/migrations`.
   - SQLite migrations go in `database/sqlite/migrations`.
   - MySQL migrations go in `database/mysql/migrations`.
   - Use matching version prefixes for the same logical migration in every backend.
   - Filename format is `<version>_<name>.up.sql`, for example `20260722000_widgets.up.sql`. The bootstrap `20260503000_schema_migrations.sql` intentionally omits `.up`: it initializes migration bookkeeping separately from the versioned batch.

2. Versioning rules.
   - Migration versions are parsed from the filename prefix as `int64`.
   - Migrations are sorted by version and applied when `version > schema_migrations.version`.
   - Do not reuse a version. The migration loader rejects duplicates.
   - Use a monotonic timestamp-style version. If adding multiple migrations on the same day, increment the suffix: `20260722000`, `20260722001`, etc.
   - Every runner locks before reading the version. PostgreSQL and SQLite share `database.ApplyMigrations` for the pending-file loop only; each backend keeps lock acquisition, bootstrap and transaction ownership explicit. Postgres and SQLite apply the pending batch in one transaction, including version updates; a failure rolls back the entire batch. MySQL DDL commits implicitly, so its runner uses `GET_LOCK` on a dedicated connection and commits a pending marker before each migration. It records completion and clears the marker atomically. An unfinished marker blocks startup; follow the MySQL migration recovery procedure below. A competing startup may fail with a lock error and must be retried after the first finishes.

3. Add sqlc queries.
   - Postgres query files go in `database/postgres/queries`.
   - SQLite query files go in `database/sqlite/queries`.
   - MySQL query files go in `database/mysql/queries`.
   - Keep query names and behavior aligned across every backend when they implement the same app operation.

4. Generate database code.
   - Run `go generate ./database` after migration or query changes.
   - This runs `go tool sqlc generate` using `database/sqlc.yaml`.
   - Generated code lands in ignored backend `db` folders; adapters in `database/postgres/queries`, `database/sqlite/queries`, and `database/mysql/queries` are source files and should be updated manually.

5. Update the database interface and wrappers.
   - Add app-level models to `database/models.go` when generated row types should not leak out.
   - Add methods to the domain interfaces composed by `database.Querier`, or to `database.Database`, only for operations needed by application code.
   - Implement each new `Querier` method in `database/postgres/queries`, `database/sqlite/queries`, and `database/mysql/queries`.
   - Update `database/cached.Querier` so it still satisfies `database.Querier`.

SQLite constructor options configure DSN parameters for every new connection. Use `WithForeignKeys` for foreign-key enforcement; pool limits are configured separately in the constructor. MySQL accepts either a driver DSN (`user:pass@tcp(host:port)/dbname`) or a `mysql://user:pass@host:port/dbname?param=value` URL. Every backend initializes the migration table from its embedded `migrations/20260503000_schema_migrations.sql` file.

SQLite with the default filesystem VFS creates new directories with `0700` and new database files with `0600`. On Unix, existing database/journal/WAL/SHM files must have no group/other permissions; startup rejects broader modes, symlinks and non-regular files. Stop the service before correcting permissions on its own storage files. Existing directories are not chmodded: use a service-owned directory that other users cannot modify. New SQLite journal/WAL/SHM files inherit the private database permissions. In-memory databases skip filesystem preparation; URI `mode=ro/rw` never creates a missing database. URI `modeof` is rejected because SQLite can use it to override the private file mode. Custom VFS permissions and Windows ACLs are deployment responsibilities.

## MySQL migration recovery

The bootstrap creates `schema_migration_pending` for new and existing databases.
This cannot detect partial failures that happened before this protection existed.
If startup reports an unfinished migration:

1. Stop all application instances and back up the database.
2. Read `version` from `schema_migration_pending WHERE id = 1` and from `schema_migrations WHERE id = 1`. An absent completed-version row means zero. Inspect the matching file in `database/mysql/migrations` and determine which schema and data changes actually completed.
3. Either restore the database to its pre-migration state before clearing the marker and retrying, or manually complete and verify all remaining changes. Do not blindly clear the marker, replay a partially applied file, or edit a published migration.
4. If completing manually, record the actual pending version and clear the marker together, replacing `<version>` below. Only do this after repairing and verifying the schema and data:

   ```sql
   START TRANSACTION;
   INSERT INTO schema_migrations (id, version) VALUES (1, <version>)
     ON DUPLICATE KEY UPDATE version = VALUES(version);
   DELETE FROM schema_migration_pending WHERE id = 1;
   COMMIT;
   ```

5. Restart the application and verify that later migrations complete.

## Caching Guidance

Cache only database reads that are stable, frequently reused, small, and have clear invalidation rules.

Good candidates:

- Account profile lookups by subject.
- Other read-only reference data or low-churn configuration rows.

Avoid caching:

- Authentication identity, account roles, and permission checks.
- OTP/login/email-change requests.
- Refresh-token consumption or revocation flows.
- One-time, security-sensitive, or mutation-coupled reads.
- Large result sets or unbounded user-specific lists.
- Reads inside transactions unless the wrapper is explicitly designed for transaction consistency.

Implementation notes:

- Keep cache keys in `database/cached/internal.go`.
- Share one `cached.Database` wrapper per database in a process. Its bounded generation shards prevent reads from repopulating stale entries after invalidation, including when cache deletion fails. Transactions bypass cache reads and invalidate only after commit; cache failures fall back to the database.
- The server always enables the cache. Invalidation is local to its wrapper: writes from other processes or directly to the database can leave cached profiles stale until expiry (TTL starts when the read is cached). Cross-instance immediate freshness would require distributed invalidation. Authentication identity, roles, permissions, OTPs, and refresh tokens currently bypass the cache.
- `memory.New` defaults to 1024 entries, 8 MiB of key/value bytes, and a 20-second TTL. It evicts the oldest written entry and cleans expired entries in the background. Configure limits with constructor options; always close the store when its owner shuts down.
- Cache JSON structs/slices inside `database/cached` when useful; keep the public `cache.Store` byte-oriented.
- Invalidate related cache keys immediately after successful writes outside transactions. Inside transactions, collect keys and invalidate only after a successful commit.
- Ignore best-effort invalidation errors only after the database write succeeds.
- Use the request `ctx` for cache reads/writes. If invalidation must be best effort after a successful write, keep the existing pattern deliberate and localized.

## Permissions and Roles

- `auth.Authenticator.RevokeAll` rotates the account's `auth_id` and removes its refresh tokens atomically. Issue and Refresh lock the account before writing/consuming refresh tokens; each refresh token carries the generation that issued it. Keep these reads uncached. A fresh Issue ordered after revocation creates a new valid session; requests authenticated before revocation may finish.
- All new account/session generations use `database.NewAuthID()` (256 random bits encoded as 64 lowercase hexadecimal characters). Migration `20261106000` widens MySQL storage and preserves existing generations and sessions; do not rewrite old identities merely to normalize their representation. Deploy with old application writers stopped.
- Session migration `20261105002` backfills existing refresh tokens with their account's generation, preserving existing sessions. Stop old application versions during deployment; old token writers do not populate the new column. This change does not add token-family replay detection or a new logout endpoint.

- Role and permission identifiers are i18n keys, defined in `database/models.go`.
- Add locale labels for new keys in `i18n/en.go` and `i18n/es.go`.
- Store role and permission relationships in the database through migrations.
- JWT claims may carry roles, but permission membership should be checked from the database.
- To protect an endpoint, use `RequirePermission` with the specific permission key. Add a role-specific wrapper in route registration only if it meaningfully improves readability.

## Localization and Errors

- `handlers.Handler.localize` is the single handler-owned request localization helper.
- Handlers and middleware receive the minimal `internal/logging.Logger` interface; use `logging.RequestArgs` for request log fields.
- Middleware receives `middleware.LocalizeFunc`; do not pass the whole handler or full `*i18n.Localizer` into middleware.
- API errors should be JSON objects shaped like `{"error":"..."}`.
- Use `h.writeError` when there is an underlying error to log.
- Use `h.writeStatus` when there is no underlying error.
- Keep localization keys short and stable, and keep log messages descriptive.

Example:

```go
h.writeError(
	w,
	r,
	http.StatusInternalServerError,
	err,
	"err.select_widget",
	"failed to select widget",
	"widget_id",
	widgetID,
)
```

## Email delivery

- The app is intended to run behind a reverse proxy. Apply per-client-IP throttling at that proxy to the OTP routes (`/auth/login`, `/auth/verify`, `/account/email/change`, `/account/email/change/confirm`, with the configured root prefix). The application enforces persistent budgets by normalized email for login and by authenticated account for email changes; it does not impose peer-IP or global OTP budgets. Keep identity budgets even when proxy limits are enabled.

- Handlers receive `github.com/tavocg/go-email/mailer.Mailer` through `handlers.Options`.
- `cmd/server.go` injects `app/mailer/noop.Mailer` by default. Replace that provider with an SMTP or Mailgun client to deliver messages; handlers remain unchanged.
- Configure the sender with `mail.from` / `--mail-from` / `APP_MAIL_FROM`.
- OTP messages use localized plain text and the request context with a delivery timeout. Save the challenge before sending; do not delete it on ambiguous delivery failures or reset abuse limits.

## Configuration

- Database maintenance runs at startup and every minute, outside HTTP handlers. Each pass deletes up to 1000 expired rows per OTP/refresh-token table and 100 rate-limit rows, with a five-second context deadline. Failures are logged and retried on the next pass; shutdown cancels and joins the worker before closing the database. Cleanup is retention maintenance, not an abuse quota.

- Add new runtime settings in `cmd/serve.go`.
- Add the key, flag, help and default together in the settings table. Keep `runServerFromConfig` and the `serverConfig` fields in `cmd/server.go` aligned with it.
- Avoid adding configuration until the code path actually needs it.
- Verification codes are stored only as HMAC-SHA-256 digests bound to purpose and identity using `github.com/tavocg/go-secrets/otp`. Configure an independent `otp.secret`; never reuse the JWT signing secret.
- Outside `--dev`, startup requires both `auth.secret` and `otp.secret` to contain at least 32 bytes. Development allows empty or short secrets with warnings; an empty OTP secret uses a random per-process key, so pending codes do not survive restarts. Equal nonempty secrets are rejected in both modes. Keep this policy in runtime wiring; reusable constructors retain their own contracts. The README quick start uses `go run . --dev`.

## Verification

Run the focused generation command for what changed, then run the project checks:

```sh
go generate ./...
go test ./...
```

Only run the generation commands relevant to the files changed. Do not add new tests unless explicitly requested, but do run existing tests before reporting completion.

CI runs the existing tests with `-race` and checks Go vulnerabilities before building release artifacts. Keep build/test jobs at `contents: read` with checkout credentials disabled; only the tag-push publication job may request `contents: write`, and it must depend on the successful build job and consume that run's artifacts.

The authentication integration suite always runs SQLite. Set `TEST_POSTGRES_DSN` (PostgreSQL URL) and `TEST_MYSQL_DSN` (MySQL driver DSN) to include external backends; CI supplies disposable service containers for both. These test users need CREATE/DROP DATABASE rights: each case creates and removes a randomly named database. Missing variables skip those backends locally; a configured but unreachable backend fails the tests.

## Naming and adapters

Use `EnsureAccountByEmail` for create-if-missing semantics and Go initialisms `SQLite`, `MySQL` and `OTPHash`. sqlc renames `otp_hash` to `OTPHash` for every backend. Convert compatible generated row structs explicitly to application models; keep driver-specific error mapping in each adapter. `database.Querier` composes account, session, permission, OTP, rate-limit and maintenance interfaces.

Account-owned email-change challenges, roles and refresh tokens cascade on account deletion on every backend. Migration `20261106001` preserves valid pending SQLite challenges, discards orphaned ones and removes `accounts_meta`; profile queries read explicit columns from `accounts` directly.

OTP routes use the typed purposes in `handlers/otp.go` for signing, mail keys and persistent quota scopes. Issuance remains one per minute and five per ten minutes; verification remains five per ten minutes, independent of challenge replacement or consumption.

Cache operations require a non-nil context, as does the mailer; `cache.ErrNilContext` reports invalid calls without a panic. SQLite path parsing, private creation and existing-file validation are separate helpers; URI `mode=ro/rw` does not create missing files or directories.

Published migrations are immutable. The stored version prevents replay; do not add `IF NOT EXISTS` retroactively or hide schema drift. On MySQL, inspect and repair partial DDL using the pending-marker recovery procedure instead of rerunning a migration blindly.
